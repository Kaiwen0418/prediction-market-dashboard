# 钱包覆盖与看板内存修复

2026-11-02，伦敦时间。已在本地测试机器部署。

## 原因

钱包日汇总采用 200,000 个单元的固定准入限制，满额后新钱包/日期会被跳过。此外，FIFO 只要碰到一个旧引用就删除整行汇总，会一并丢掉同一单元中较新的成交贡献。这是汇总层额外产生的覆盖损失。

看板后端接近 1 GiB，cgroup 中约 1.03 GB 是匿名进程内存，磁盘文件缓存只有几 MiB。响应缓存只限制 2,048 条，不按体积限制；TTL 过后仅返回未命中，并不释放对象。全量分页的原始 JSON 也进入缓存，同时目录服务还保存压缩字段后的快照。游标更换产生新 URL，旧的大对象持续留存。

## 修复

- 每张原始凭据保存紧凑的钱包贡献，事务内记录是否处理。日汇总成为贡献的派生视图，去掉 20 万单元门槛和每单元 64 引用截断。FIFO 仅移除到期凭据的贡献，保留同单元的较新部分。
- 从仍保留的规范化成交补建，每轮最多 50 个凭据、两秒协作预算；实时采集继续。凭据账本保证重复补建不重复计数，补建完成前暂停生成新的慢建仓候选。旧截断汇总产生的案件保留版本并标为已被替代。
- 已过期或根本未观察到的原始成交无法补出。新增贡献仍计入原有 20 GiB 数据库、5 GiB raw 预算；数据保留时间仍可能因容量缩短。这里的完整性是“留存且可归因的输入”，不是全平台或完整七日历史。
- 高成交合约超过 5 万笔时，按 13 小时、65 分钟、13 分钟、7 分钟缩短回放范围，保留能完整计算的短窗口，明确记录省略的窗口。七分钟保留最低六个一分钟基线；未读历史保持未知，不能当作零。最短范围仍超预算则明确拒绝评分。
- 看板响应缓存改为压缩 JSON 的 LRU：最多 256 条、压缩内容 32 MiB、序列化 JSON 总量 64 MiB，单条超过 8 MiB 不缓存。保留请求合并和允许的失败回退；每分钟清理过期对象。
- 批量目录分页不再进入响应缓存，目录服务沿用其紧凑快照与失败回退。监控状态提供缓存字节数和进程内存指标；保持原来的监控数量和 1 GiB 容器内存上限。

## 验证

91 项调查测试、59 项看板后端测试通过，新增验证包括超过旧 20 万门槛、同单元只回收旧贡献、补建去重、旧案替代、高成交短窗及未读基线未知、未来时间记录不丢失且不提前触发、缓存字节预算、LRU、到期释放及读者无法修改缓存。

|---|---:|
| 符合条件的留存源成交 | 534,069 |

源计数按原始凭据使用成交索引读取，在同一 MVCC 快照核对；避免按钱包顺序随机读取整个大表。[实库对账](coverage-memory-rollup-audit-2026-11-02.json)。

模拟 1,200 个不同响应的压力测试：单个示例 JSON 为 242,780 字节，解码为 Python 对象约 759,986 字节。若独立保留 2,048 份，粗略对象体积约 1.45 GiB；这说明条数限制无法约束 RAM，并非对旧进程的逐对象堆分析。新缓存该测试仅保留约 12.9 MiB 压缩内容，测试进程峰值约 62.8 MiB。[缓存压力结果](coverage-memory-cache-benchmark-2026-11-02.json)。

部署热身后的看板 RSS 约 150 MiB；该数值是短时运行观察，缓存预算不等于整个进程的硬内存上限，并发请求仍需要工作内存。看板仍监控每平台 10 个 hot、30 个 warm；调查深采预算不变。
