# 容量回收导致持续负载的修复

2026-10-30，伦敦时间。机器为 i7-1360P、16 逻辑线程。

## 故障与根因

检查时调查 PostgreSQL 持续占用约一个核心（容器约 91% CPU），封装温度采样约 69–80°C，整机仍约 90% 空闲。容量水位在约 16 GiB 时触发，`CREATE TEMP TABLE capacity_cases` 已运行超过 6 小时 40 分钟，持有独占证据锁；两平台最后接收时间停在 02:11。

执行计划显示，对约 7,000 个案件使用相关子查询，反复扫描约 1,037 万条成交。旧实现还把 PostgreSQL 已分配空间与仍在使用的空间混同，并在每一轮对所有表执行 `VACUUM FULL`；小样本验收没有覆盖这一级别的数据量。

## 改动

- 案件直接 receipt 引用、观察区间引用分别保存为 GIN 索引数组，保存新版本时累计旧引用。旧案按 100 条一个事务补建；仅无直接来源的旧格式案件才按成交主键 `(venue,id)` 补齐引用。
- 回收按原始凭据批量查找受影响案件，不再逐案扫描逐笔表。大数组谓词采用事务内的位图索引路径，并关闭这一步的 JIT；实测默认规划器可能低估数组比较成本，改走主键全扫描，因此不能只依赖“索引存在”。观察凭据查询采用其索引。
- 默认每分钟最多回收 500 个旧 receipt。单条清理 SQL 超时 15 秒，获取维护锁限时 1 秒；失败记录 SQL 模板和阶段，不记录绑定参数，并退避五分钟。每轮还检查协作式工作预算，预算不是整轮硬实时保证。
- 普通清理只 VACUUM 发生变化的表。删除证据和孤儿文件完成后即释放应用独占锁，普通 VACUUM、空间测量允许 API 读取。Store 事务设置 30 秒 SQL、2 秒锁超时；API 返回可重试的 503。
- 用 PostgreSQL `pgstattuple_approx` 估计 heap/TOAST 的可复用空间，索引空间保守全额计入。区分 `database_bytes`（已分配）和 `database_used_bytes`（扣除可复用空间），估计缓存最多 120 秒。
- 80%→60% 的清理水位按使用量执行；物理数据库 20 GiB、raw 5 GiB 准入上限仍有效。只有到达物理上限、单表空洞至少 128 MiB 时才尝试压缩一张表，限时 45 秒、每小时至多尝试一次。失败不允许无限重写。WAL 和重写临时空间仍需要额外磁盘余量。
- 七日保留也复用案件证据索引，保留新版本此前的证据引用。

## 实库验证与恢复

先停止失控 worker 和查询，PostgreSQL CPU 降至接近 0%，最高温度读数约 53°C。随后在现有数据库进行明确的受控修复，未复制或回放整库来压测。

- 千万级逐笔库上，500 个旧 receipt 的案件依赖查询实测约 86–105 ms，执行计划不访问逐笔表。
- 受控恢复每轮两个 500-receipt 批次，实测整轮约 3.3–18.7 秒，最终使用量回到准入水位以下。常驻默认随后降为每轮一个批次。
- 两平台已在 09:28 再次收到新成交。02:11 起的采集缺口以 `collection_restart_gap` 显式保存；自动交易采集游标从普通冷启动窗口重新开始，避免补跑停采积压，人工补采任务保持原状态。
- 84 项调查模块测试通过，包括真实 SQL 超时/锁释放、API 503 与恢复、普通维护阶段允许读取、旧格式引用、历史版本引用、索引执行路径和大观察表下的案件写入。
