# Market Surveillance 性能与存储评估（2026-10-28）

结论：可以在 `frodo@192.168.1.131` 上运行测试版。先部署每个平台 20 个深度采集合约，保留全市场目录与探索配额；暂不合并 PR。当前单进程 REST 架构不具备 200 个合约每分钟完整采集的能力。数据从空库开始，不迁移 Railway 的测试数据。

## 实测环境与方法

- Ubuntu x86_64，16 线程，约 14.8 GiB RAM；检查时约 7.8 GiB 可用、根盘约 300 GiB 空闲。
- Docker / Python 3.12 / PostgreSQL 17，独立 Compose 项目 `prediction-market`。
- Worker 上限 2 CPU / 1 GiB，后端 2 CPU / 1 GiB，调查 API 1 CPU / 512 MiB，数据库 2 CPU / 768 MiB。
- 测试时主机上的其他项目及本项目真实采集同时运行；这不是独占机器测试。
- 模拟成交包含 12 小时历史及近期突增，主动制造候选案件。每次基准测试创建随机数据库 schema，退出后删除；原始模拟数据使用临时目录。
- 以下结果是本次样本，不能当成任意市场的持续吞吐保证。原始测量 JSON 位于 [benchmarks/surveillance/2026-10-28](benchmarks/surveillance/2026-10-28)。

## 成交与案件回放

200 个合约、每个 1,000 笔成交，共 200,000 笔；回放 20 个合约。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 归档、规范化落库耗时 | 35.871 s | 22.303 s |
| 落库吞吐 | 5,575.6 笔/s | 8,967.2 笔/s |
| 每页 P95 | 248.53 ms | 128.32 ms |
| 单合约回放 P95 | 165.77 ms | 162.45 ms |
| 基准进程峰值 RSS | 108.6 MiB | 109.0 MiB |
| 成交表（含索引、TOAST） | 141.16 MB | 147.77 MB |
| 原始 Parquet | 6.08 MB | 6.08 MB |

吞吐提升约 61%，本地处理耗时下降约 38%。最终成交表增加约 6.6 MB，来自支持有序、有上限回放的索引；不是存储下降。原始唯一数据本身不会因去重而变小。

新增“高活跃单合约”测试：2 个合约、每个 50,000 笔成交。合计落库 6.63 秒；回放 P95 920.37 ms；进程峰值 RSS 425.1 MiB；生成的案件平均 JSON 约 1.05 MB。

因此首版将每次回放上限设为 50,000 笔。超过时 API 返回 HTTP 413，worker 记录容量缺口，不截断后继续给分。高于该规模需要分段聚合或单独扩容，不能只增加订阅数量。

## 全市场目录选池

100,000 个模拟合约，每个附约 1.4 KB 规则文本。两种方式选出的 100 个合约完全一致。

| 实现 | 选池耗时 | 进程峰值 RSS |
| --- | ---: | ---: |
| 整表加载 | 1.590 s | 515.6 MiB |
| 服务端游标 + 有界候选池 | 3.548 s | 83.2 MiB |

流式方式用额外约 2 秒换取约 84% 的峰值内存下降。候选池最多保留约两倍预算数量的文档，数据库游标每次取 256 条；不会随全部目录数量保留所有 Python 对象。

此测试只验证目录选池。完整发现所需时间仍由真实市场数量、分页速度和接口限流决定；目前没有可靠的全平台市场总数，不能报告“全市场覆盖率 100%”。

| --- | ---: | ---: | ---: |
| `/health` | 50/50 | 7.83 ms | 23.05 ms |

这是容器内部的短时缓存命中测试，不包括公网 RTT，也不是长时间负载测试。公网 REST 检查中，健康、目录、市场上下文、行情、research 和 readiness 均已返回 200，readiness 为 true。打包时补上了现有后端所需的 `public/data`，修复了容器初次启动时 research 缺文件造成的 500。

浏览器中仅临时把 REST fetch 从 Railway 地址改写到新入口，切换交易对可成功请求新后端；标准交互复测没有运行时异常。SSE 未在这次浏览器改写中迁移。程序化强制导航的另一次试验曾产生 Globe 生命周期异常，未把该试验算作浏览器通过结果。截图保留在 `tmp/surveillance-migration/vercel-rest-rehearsal.png`。

最终常驻容器快照：backend 392.8 MiB、worker 93.5 MiB、调查 API 54.5 MiB、PostgreSQL 166.2 MiB，合计约 **707 MiB**。这是当时实跑快照，不是峰值承诺。目录已发现约 209,900 个合约，40 个成交任务、40 个检测任务处于启用状态，任务失败数为 0；完整目录仍在分页发现中。所有测试/基准临时 schema 已删除。

## 存储模型与预算

当前模拟样本成交表约 **739 B/笔**（含索引、TOAST），Parquet 约 **30 B/笔**。模拟字段重复较多，实际 raw 压缩率可能显著更差；不能用 30 B/笔作为生产预算。

仅按成交表推算，不含目录、原始响应、案件、WAL、空闲页和临时文件：

| 每日新增成交 | 每日成交表增量 | 8 天事件数据量 |
| --- | ---: | ---: |
| 100,000 | 约 74 MB | 约 0.59 GB |
| 1,000,000 | 约 739 MB | 约 5.91 GB |
| 10,000,000 | 约 7.39 GB | 约 59.1 GB |

每分钟轮询一次、每个合约仅一页时：

| 总深度合约数 | 每日请求数 | 若每次产生新的 30 KiB 正文：raw/天 | 同样情景保留 8 天 |
| --- | ---: | ---: | ---: |
| 40（20/平台） | 57,600 | 约 1.77 GB | 约 14.2 GB |
| 200（100/平台） | 288,000 | 约 8.85 GB | 约 70.8 GB |

这只是明确假设下的情景推算。多页、重试和目录请求会增加开销；相同正文去重会减少 raw 文件占用。每次请求仍保留独立 PostgreSQL receipt，不能按文件去重率把 receipt 开销也归零。样本中 receipt 和相关索引约 1 KB/条，40 合约每分钟轮询约再增加 60 MB/天。

早期真实目录样本中，当前目录加规则约为每个合约数 KB。按 5 KB/合约粗估，100,000 合约约 0.5 GB、1,000,000 合约约 5 GB；这不是已核实的平台合约总数，也不含 raw 和历史规则变化。

样本 60 个案件及初始版本合计约 1.1 MB，平均每案约 18 KB 物理表空间，JSON 平均约 24 KB。高活跃市场的案件可达到 MB 级，不应按普通样本估算所有案件。

## 已落实的开销控制

1. 使用 psycopg 批量执行写入成交，保持整页数据与 checkpoint 同一事务。
2. 原始正文按 SHA-256 内容寻址：相同正文共用一个 Parquet blob，但来源、参数、时间、状态仍逐次记录在 PostgreSQL。Parquet 内元数据描述首次归档；每次 receipt 的数据库元数据才是本次来源与时间的依据。
3. 规则仅在相对上一次观察发生变化时增加版本；规则回退到旧内容仍会增加一次新观察版本。已关闭 Polymarket 目录完成后每周重扫，其他目录完成后每小时重扫。
4. 自动候选按平台、合约、结果和窗口在一小时内合并；异常分数提高至少 20 点时允许新建案。显式人工回放仍完整计算，worker checkpoint 显示新建与合并数量。
5. 目录选池与原始校验使用服务端游标。回放默认最多 50,000 笔，超限显式报错。
6. 每小时进行有批量上限的测试数据清理：案件和覆盖日志保留 7 天；成交与无引用 raw 至少保留 8 天，为案件基线留一天余量。保留案件所引用的成交/raw、当前目录、最新规则和人工信息仍受引用保护，故不是硬性全库 8 天清空。
7. 删除失效的暂停任务和过期非当前规则版本。PostgreSQL 删除后的空间由 autovacuum 回收复用，文件占用不会立即缩小；目录、WAL、索引和引用中的证据仍需计入磁盘预算。
8. 每个 Python 服务日志轮转为 2×10 MB。进程设置 CPU/内存上限；这些是保护测试机的运行上限，不代表预留内存或已测最大吞吐。

## 仍需观察的边界

- 一个 worker 的 HTTP 请求间隔为 0.6 秒：200 合约仅发请求就至少 120 秒；40 合约至少 24 秒。检测、分页、归档、目录扫描和上游延迟都在此基础上追加。`poll_seconds=60` 是再次到期时间，不是每分钟覆盖 SLA。
- 采集池中的大量冷门/组合市场可能几乎无成交，短时实跑不能代表热门合约的成本。
- 本次没有 7 天连续观察、百万级合约发现实测、持续高并发 API 压测或突发网络故障长测。保留策略与游标恢复有集成测试，但不能据此声称已经完成长期容量校准。
- 每小时清理有批量上限。若输入增速超过清理速度，磁盘仍会增长；引用保护和尚未清理的孤立文件也可能使保留期延长。只运行一个采集/维护 worker，避免内容寻址文件清理与其他写入者竞态。
- 增至 100 合约/平台前，应先看真实请求时延、任务到期积压、每日新增成交、正文唯一比例和磁盘日增量，再决定并发、轮询周期与预算。
